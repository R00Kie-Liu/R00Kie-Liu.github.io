# 自然、直接的中文与学术写作

把“去 AI 味”理解为编辑质量问题，不追逐检测器分数。先修正问题意识、论证推进和中文节奏，再处理高频词与标点。

## 自动判断场景

保留技能名 `polish-technical-blog-zh`，作为统一入口；无需安装或调用其他写作技能。根据用户目标、文档体裁与当前段落自行判断，不要求用户选择模式，不向用户展示内部路由。

| 场景 | 编辑重点 | 按需参照 |
| --- | --- | --- |
| 技术博客、教程、推导长文 | 问题驱动、解释和中文节奏，保留探索与反例 | 中文稿读 ai-tells-zh；推导型风格读 reasoning-blog-style |
| 论文、摘要、引言、贡献、实验、基金申请、rebuttal | 主张与证据对应，贡献明确，实验各有论证职责 | 读 academic-writing；中文稿同时读 ai-tells-zh |
| 技术方案、SOP、报告、README、专业解释 | 结论、动作、条件和依据直接呈现 | 中文稿读 ai-tells-zh；防御表达明显时读 anti-defensive-writing |
| 指定段落或短回复的润色 | 只做局部表达优化，不启动全文结构重写 | 防御表达明显时读 anti-defensive-writing |

混合文档按章节功能处理，例如论文综述型博客使用博客结构，转述他人贡献时保留归属。英文论文沿用英文，仅应用论证与反防御规则，不套中文语法建议。普通问答无需强行触发全文编辑、补写章节或运行长文脚本。

先按场景组织内容，再在同一份稿子中调整表达，最后做一次反防御核对；不让三套规则依次全文重写。共同底线优先于场景偏好，用户样文优先于默认文风。

## 共同的反防御原则

直接呈现主张、动作与证据。删除没有信息的预防性辩解、重复免责声明、仪式性谦虚和机械“不是 X 而是 Y”。真实的概念区分、纠错和对比应保留。

删除限定前，判断删除后是否改变有效性、证据强度、适用条件或读者理解；会改变就保留或等义改写。必要条件应贴近依赖它的主张，不能为保持摘要或结论简洁而移走。必要限制写清一次，独立阅读的章节可以保留必要重复。

把空泛退缩改成已有材料支持的具体范围；不得凭空补条件、推断机制、把相关性写成因果或把“提示”升级成“证明”。“可能”“仅”“尚未验证”和负面结果按含义判断，不列禁词。不要把尚无依据的反驳写进正文。

详细判断与例子见 [references/anti-defensive-writing.md](references/anti-defensive-writing.md)。论文专项见 [references/academic-writing.md](references/academic-writing.md)。

## 读取参照

- 编辑中文正文时读取 [references/ai-tells-zh.md](references/ai-tells-zh.md)，按中文语境识别问题，不套用英文禁词表。
- 用户希望文章接近“科学空间”这类推导型技术博客时，读取 [references/reasoning-blog-style.md](references/reasoning-blog-style.md)。只迁移高层写作方法，不复刻具体作者的独特措辞、口头禅、经历或人格。
- 若项目中有 `AGENTS.md`、写作规范、术语表或用户自己的旧文，优先级依次为：用户本轮要求 > 用户自己的样文 > 项目规范 > 本技能参照。

## 确定任务模式

1. **审稿**：只标出 AI 腔、论证断点和事实风险，不改正文。
2. **轻改**：保留段落顺序，只修病句、套话、重复和局部节奏。
3. **深改**：允许拆并段落、移动论据、重写开头与结尾，但不改变事实和立场。
4. **起草**：根据用户材料写新稿；材料不足时保留缺口或提出需要补充的事实，不自行编造。

未指定时：已有完整草稿用“轻改”；用户明确说“重写”“结构也改”时用“深改”；只有提纲或资料时用“起草”。

## 建立保护清单

改写前在内部列出不可漂移的内容：

- 人名、机构、模型名、版本、数字、日期、单位与比较关系；
- 公式、变量、代码、命令、URL、引用、脚注与 Markdown frontmatter；
- 结论的强弱、因果方向、适用条件、反例和作者明确表达的不确定性；
- 领域术语及项目已有的中英文写法。

不要为了增加“人味”捏造场景、实验、数字、引语、个人感受或来源。原文若只有泛泛判断，应收紧表达并指出材料不足，而不是补一个看似具体的故事。

## 编辑流程

### 1. 钉住文章真正的问题

用一句内部摘要写清“文章试图回答什么”。检查每节是否推进这个问题。删去或合并只重复主题、不增加机制、证据、例子或边界的段落。

技术博客优先采用以下推进链，按材料删减，不要硬凑齐：

`观察或疑问 → 已有解释 → 不足之处 → 定义与假设 → 推导或实验 → 反例/边界 → 当前结论`

章节标题应描述当前推理动作或对象，如“问题”“推导”“梯度”“实验”“局限”，不要让每节都变成“背景—优势—挑战—展望”。

下述开头与结尾建议主要用于博客；论文结构按 academic-writing 处理，方案和短回复按当前任务组织。轻改不主动重写开头或结尾。

### 2. 重写开头

从真实触发点、明确问题、现有方法的矛盾或一个具体例子开始。允许直接写“最近读到……”“这里有个问题……”“通常的做法是……，但……”。

删除宏大背景、行业浪潮和“本文将全面深入探讨”。技术文章不必强行用故事或电影式场景开头。

### 3. 推进论证

- 每个判断尽量回答“为什么”，给出机制、公式、实验、来源或例子中的至少一种支撑。
- 遇到“有研究表明”“专家认为”等缺少出处的归因，不要编造来源，也不要在润色时悄悄洗成无来源的确定事实。保留必要的原始语气，并把它列入交付时的“待补证据”。
- 用设问推进真正的推理，并尽快回答；不要连续抛出只为制造气势的问题。
- 抽象概念难懂时，用短而准确的日常例子搭桥，随后回到正式定义。
- 允许写“这里不够严谨”“这个结论只在……成立”“暂时没有实验验证”。诚实的边界比补齐一套漂亮叙事更可靠。
- 保留必要的重复术语。不要为了避免重复而轮换同义词，导致概念漂移。
- 让段落长短服从内容。推导段可以长，转折或结论可以短，不按固定句长制造所谓 burstiness。

### 4. 清理中文表面痕迹

按 [references/ai-tells-zh.md](references/ai-tells-zh.md) 处理翻译腔、空泛大词、机械三段式、虚假对称、无依据的个人偏好、模糊归因、客服话术和模板结尾。

不要执行脱离样文的硬禁令：

- 不一律删除破折号、分号、长句、第一人称复数或技术小结；只处理密度异常和用法空泛的情况。
- 不强制加入碎句、口语、自我打断、跑题或“真实感”细节。
- 不把所有列表改成段落。步骤、条件、对照和参数表保留列表更清楚。
- 不因某个词常见于模型输出就机械替换；若它在当前句中准确、自然且有信息，保留。

### 5. 收束结尾

回到开头提出的问题，说明已经得到什么、依赖哪些条件、还缺什么。可以有技术小结，但不要突然上升到时代、生态、未来无限可能，也不要添加“希望本文有所帮助”“让我们拭目以待”。

### 6. 核对保护清单

逐项对照原文。任何数字、限定词、否定、比较级、公式符号、链接或引用发生变化，都要确认是用户要求或明确纠错；否则恢复。

## 运行机械审稿

对本次起草或修改的超过约 800 个中文字符的连续正文，运行（短回复、英文稿和仅审结构时跳过）：

技能目录可以位于仓库或用户目录中的任意位置。所有 `references/` 和 `scripts/` 路径均相对于本次实际读取的 `SKILL.md` 所在目录。调用脚本前，将 shell 变量 `SKILL_DIR` 设为该目录的绝对路径；保留正文文件所在的工作目录。审稿脚本仅依赖 Python 3 标准库，无需安装第三方包。

```bash
python3 "$SKILL_DIR/scripts/audit_zh_blog.py" path/to/post.md
```

粘贴文本可走标准输入：

```bash
python3 "$SKILL_DIR/scripts/audit_zh_blog.py" - < draft.md
```

脚本只提供可定位的启发式命中，不给“AI 概率”。逐条判断语境；不要为清零而牺牲准确性。改写后再运行一次，确认高优先级套话减少，并检查新文本没有引入新的模板句。

## 输出

- 用户给出文件并要求修改：直接编辑文件，返回简短变更摘要和验证结果。
- 用户粘贴文本：默认先给完整改写稿；只有用户要求时才附逐条修改说明。
- 审稿模式：按“位置—问题—为什么—建议”报告，不重写未授权段落。
- 若仍有缺失来源、无法核验的数据或语义歧义，在正文后单列“待补证据”；这类风险不能被文风润色掩盖。
- 不声称“通过 AI 检测”“AIGC 率降到 X%”或“保证像真人”。可以说明已减少哪些可观察模式。
