# 中文技术博客常见 AI 痕迹

把本表当作审稿线索，不是禁词表。单个命中通常不能说明问题；同一段里多种模式叠加，才值得优先重写。

## 1. 空转开头

常见形状：

- “在当今快速发展的数字化时代……”
- “随着人工智能技术的不断演进……”
- “在科技日新月异的今天……”
- “本文将全面、深入、系统地探讨……”

问题不在词旧，而在这些句子没有缩小题目。改成真实触发点、明确疑问、已有方法的缺口或一条具体观察。

## 2. 翻译腔和名词堆叠

重点检查：

- “对于 X 来说”“基于 X 进行 Y”“围绕 X 展开”“使得 X 得以 Y”；
- 连续使用“实现、进行、提供、赋予”承载本可直接表达的动作；
- 一句话塞入多层“的”，主语和动作迟迟不出现；
- 英文抽象名词逐词映射成“范式、格局、生态、维度、路径”。

优先找回谁做了什么、在什么条件下得到什么结果。

还要检查“看”是否被当成万能动词反复使用。技术文里“可以看”“先看”“从 X 来看”“看 X 的影响/成本/效果”经常只是省事写法；根据语义改成“考虑、观察、估计、衡量、比较、分析、检查”等更具体的动作。若确实是视觉读取图表、代码或日志，可以保留“看”。

## 3. 没有机制的大词

高风险词包括“赋能、颠覆、重塑、革命性、里程碑、开启新篇章、深刻改变、全方位、多维度、闭环、生态”。

若后文能解释具体改变了哪一步、减少了多少成本、突破了哪个约束，可以保留判断；否则改写成动作和结果。

## 4. 机械路标

连续出现“首先、其次、再次、最后”“一方面、另一方面”“从 X 到 Y”时，文章容易像提纲展开器。

路标本身无错。问题是各段只靠路标连接，逻辑关系却没有说清。根据真实关系改成因果、递进、限制、反例或时间顺序；不需要路标时直接删掉。

“把 X 说清楚”“先把 X 讲清楚”也常见于模型生成的元话语。它的问题不在“说清楚”三个字，而在句子只承诺解释，后文却没有给出定义、条件、例子或边界。正常写法如“先把记号说清楚：这里的 $p$ 表示……”可以保留；空转写法如“接下来我们把这个问题说清楚”通常应改成具体问题或直接进入定义。

## 5. 过度工整

典型表现：

- 每节都是定义、三个分点、一句拔高；
- 连续使用“不仅……而且……”“不是……而是……”；
- 三个句子句式相同，三个段落长度近似；
- 为凑“三点”拆开同一件事，或把两点扩成三点。

打破工整不等于随机打乱。让结构服从论证：重要处多写，过渡处少写，反例可以单独成段。

另一类常见工整句是“不能只看 X，Y 也要放在一起看”“不能只考虑 X，要综合考虑 A/B 的 trade-off”“不能片面追求 X”。它们看似周全，但如果没有说清楚哪个指标在什么约束下牵制另一个指标，就只是万能平衡句。真实 trade-off 应写出被权衡的量、方向、代价和当前选择；否则直接写主导因素或当前证据支持的结论。

## 6. 模糊权威和伪具体

检查“有研究表明”“专家认为”“业内人士指出”“普遍认为”“数据显示”。若没有紧邻的来源或上下文，应补真实出处、降低语气或删去归因。

不要把模糊句改成编造的机构、年份、实验或引语。伪具体比空泛更糟。

## 7. 解释性尾巴

模型常在一句完整的话后面再挂一层“这表明……”“这意味着……”“从而进一步凸显……的重要性”。

若尾巴提供了新的推论，说明推导依据；若只是换词重复，删掉。尤其警惕每段最后都自动升格到“价值、意义、未来”。

“只保留一个判断”“最后只留下一个结论”这类话也要警惕。它常像编辑指令残留：作者没有直接给出判断，而是在说明自己要怎样收束文本。若不是在描述筛选算法、消融设置或真的只允许一个判定项，通常直接写判断本身，或者说明为什么当前证据只能支持这一条。

## 8. 客服和对话残留

博客正文中删除：

- “这是一个很好的问题”；
- “当然可以”“希望这对你有所帮助”；
- “如果你愿意，我还可以继续……”；
- “下面让我们一起深入探索”。

作者直接进入内容即可。

## 9. 装饰性排版

检查 emoji 标题、每个要点都用粗体小标题、冒号密集、无必要的全篇项目符号。技术名词、步骤、参数和对照表需要结构时应保留，不要为了“像人写”牺牲可检索性。

## 10. 模板结尾

高风险结尾：

- “综上所述……具有重要意义”；
- “展望未来……前景广阔”；
- “这只是开始”“未来可期”“让我们拭目以待”；
- 临时拔高到时代、社会或人类命运。

更合适的结尾通常是：回答开头的问题、总结最关键的推导、明确适用边界、留下一个具体未决问题或下一步实验。

“收窄结论”“把结论收窄到……”这类说法也容易像审稿意见或提示词残留。若边界确实影响结论，直接写“这个结论在……条件下成立”；需要纠正真实误解时可以保留否定。不要自动补“需要注意的是”或“这并不说明”。不要为了显得谨慎而额外加一层“收窄”的元话语。

### “能走多远”式模糊追问

检查“能走多远”“究竟能走多远”“这条路还能走多远”等说法，尤其是标题、段尾和结尾。它们常用旅程比喻代替具体问题，制造悬念却没有交代所问的是适用范围、性能上限、扩展能力、持续时间还是可行性。

根据上下文直接写出要讨论或验证的量。例如，“这种方法能走多远”可改为“这种方法适用于哪些任务”“数据规模扩大后，收益是否继续增加”或“当前结果能支持哪些结论”，只选择原文实际讨论的含义；没有依据时不要替作者补出指标或结论。若正文已经回答，直接给出结果，不再加泛泛追问。

这是一条语境审稿线索，不是字面禁令。真实行程、续航距离、引用原话或用户有意保留的比喻应按语境处理。

## 11. 伪人味

为了显得自然而硬加个人情绪、凌晨场景、朋友对话、失败经历、俚语或自我打断，同样会显得做作。只有来源材料里确有这些内容，或用户明确授权创作时才加入。

技术文里还要留意“先算 X 的账”“我们来算一笔账”这类口语比喻。若文章讨论的不是财务、预算或真实账目，它常把本来明确的对象说虚。写系统、模型或训练分析时，优先改成“X 的开销/成本/复杂度/显存占用/通信量计算”，并直接给公式或数量级。

## 12. 无依据的个人偏好

“我更倾向于”“我个人会选择”“在我看来”本身都是正常中文，不应列为禁句。模型腔通常出现在两个地方：一是作者并没有提供个人经验，却突然用第一人称模拟立场；二是句子只宣布偏好，没有交代评价标准、代价或适用条件。

例如：

> 综合来看，我更倾向于方案 A，因为它更加灵活和强大。

如果“灵活和强大”没有落到可核查的差异，这个偏好没有增加信息。应直接比较启动延迟、显存占用、实现复杂度等真实标准。反过来，如果文章确实记录作者的工程选择，并紧接着解释“为什么”，保留“我更倾向于”反而更诚实。

同一篇文章反复用“我更倾向于”给每个小节收尾时，改写其中多数；不要让它成为自动生成判断的句型。

## 13. 技术文本的特殊保护

以下内容不参与普通文风改写：

- 代码块、命令、配置、日志、API 名称；
- 行内代码、LaTeX 公式、变量、定理与引用原文；
- 模型名、数据集名、版本号、性能数字与单位；
- Markdown frontmatter、链接目标、脚注标识。

可改它们周围的说明，但不能让表达优化改变技术含义。
